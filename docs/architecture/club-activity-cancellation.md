# 社团活动取消设计（#73）

日期：2026-09-29。此文档记录实现前确认的业务与技术边界；通知系统属于 #69，不在本次改动中。

## 目标与取舍

（副）社长可以取消尚未开始的社团活动。已取消的活动继续可读，带明确状态；已存在的签到历史保留只读，不能新增签到，也不能通过待审核的修改申请再次改变活动。本次不支持重新发布、硬删除或通知成员。

使用 `club_activities.cancelled_at TIMESTAMPTZ NULL`，而非状态枚举或删除行：未取消为 `NULL`，取消后记录时间。活动是否已经开始继续由 `start_time` 判断，避免存储与时间并行变化的冗余状态。新增列的迁移对现有记录保持 `NULL`，不改变它们的读写语义；旧应用兼容新增列，但部署期间应在新应用就绪后才开放取消操作。

## 接口与展示

- `POST /api/v1/clubs/{club_id}/activities/{activity_id}/cancel` 不接收请求体，成功返回 `200 ClubActivityInfo`。鉴权复用 `ClubRoleChecker`，允许该社团的 president / vice_president（保留既有 AccessPolicy 的管理员和开发者绕过语义），service 再确认社团为 normal、活动属于该社团。未登录、无权、错误社团或不存在的活动使用既有结构化错误。
- 在活动行锁内先检查 `cancelled_at`：重复取消返回原记录，取消时间不变，即使原定开始时间已经过去。首次取消仅在锁后检查的 `now < start_time` 时写入时间；`now >= start_time` 返回 `409 CLUB_ACTIVITY_ALREADY_STARTED`。该时间比较使用带时区 UTC 时间。
- `ClubActivityInfo` 增加可空 `cancelled_at`，因此已有活动列表及社团详情内嵌的活动都能表达取消状态；活动 Ref 仍只表示身份（id/name），不承担状态或可操作性判断。同步 OpenAPI/TypeScript 类型以及新错误码的中文文案。
- 现有社团工作台为未开始、未取消的活动提供取消按钮与明确确认；成功后刷新活动数据。工作台、社团活动列表与活动详情标示“已取消”，不再把取消的活动呈现为可修改或可参加的活动。不重设计页面布局。

## 写入和并发不变量

取消使用一个数据库事务：锁定活动行，确认活动可取消，写入 `cancelled_at`，并把同一活动仍为 pending 的修改申请标记为 `superseded`。任一步失败则整笔回滚。

为避免“检查时未取消，提交时已取消”及相反的锁顺序死锁，修改申请的提交、审核批准、取消和新增签到的写路径统一以活动行锁为先。审核端可先无锁读取请求的 `club_activity_id` 来定位活动，再锁活动、锁并刷新请求，重新检查待审状态；如果请求已经被取消事务作废，不能批准。提交修改申请也在活动锁内检查未取消后创建。拒绝已取消活动上的新修改与新签到，统一返回 `409 CLUB_ACTIVITY_CANCELLED`；已经存在的签到只可读取。手工签到和扫码签到均在活动锁内做最后的取消检查，避免并发插入。取消前已经完成的历史签到不删除。

新路径使用现有事务、权限与错误响应模式。取消不改变已批准的创建申请，也不处理尚未批准的创建申请（此时尚无活动行）。

## 验证

- PostgreSQL 迁移升级后，旧活动的 `cancelled_at` 为 null；API 响应与重新生成的 OpenAPI 类型一致。
- HTTP 测试覆盖社长和副社长取消、普通成员／其他社团成员／匿名拒绝、活动归属、未开始与边界时间、重复取消幂等、取消后列表／详情可读且状态明确。
- 测试取消时 pending 修改申请自动作废、取消后无法再提交或批准修改、原有签到可读但手工与扫码新增均被拒绝；未取消活动的原有审核和签到仍正常。
- 使用真实 PostgreSQL 的独立 session 验证并发取消与修改审核、取消与手工签到的结果：不会把已取消活动重新改动或在取消后新增签到，不产生死锁或 500。前端执行类型、单测、lint、格式和构建检查。

站内信（#69）、历史记录清理、重新发布流程、通用活动状态机与纯视觉设计改版。活动 Ref 的身份契约和活动创建审核流程不变。
